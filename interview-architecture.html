Carla interview · take-home

Car Price Explorer

Internal tool to explore historical sale prices by make/model over a date range. This deck covers architecture, how to run it, assumptions, tradeoffs, and what I’d build next.

Node + TypeScript monorepo Express API React + Vite UI CSV in memory

Architecture

How the parts connect

Request flows left → right: browser UI talks to the API; the API reads sales from an in-memory CSV load and returns aggregates.

Runtime flow

What happens when you change the date range

  1. 1 UI sets from / to and calls GET /api/prices (via Vite proxy).
  2. 2 API filters in-memory sales by date + COMPLETED status.
  3. 3 aggregate.ts groups by make+model → median, avg, min/max, mileage, monthly medians, make counts.
  4. 4 UI renders KPIs + table; client-side search / top-10 make chips filter the already-aggregated rows; row click fills the sticky detail panel.
Server owns pricing math Client owns interaction filters

README · how to run

Start the project

cd carla-car-prices
npm install
npm run dev

# UI  → http://localhost:5173
# API → http://localhost:4000

Prerequisites

Node.js 20+ (tested on Node 24). No database, Docker, or env files required.

Production-ish

npm run build then npm start for the API. Frontend can be served as static files or left on Vite for the demo.

README · assumptions

What I assumed

Completed sales only

Default status filter is COMPLETED. Cancelled/returned are not closed sales for pricing.

Currency = SEK

No currency column in the CSV; amounts look Nordic; Carla is SE/NO oriented.

Grain = make + model

version is too sparse/noisy for a first “model pricing” view.

Median matters

Used-car prices are skewed; median sits next to average so outliers don’t dominate the story.

Inclusive calendar days

Date filter uses order_date as YYYY-MM-DD, ignoring time-of-day for range matching.

Node instead of Go

Brief suggested Go for the API; I chose Node/TS across the stack for speed of iteration on one language.

README · tradeoffs

Design choices and what they cost

CSV in memory

Pro: zero infra, instant queries for ~2k rows.
Con: no live reload, won’t scale to multi-GB or multi-instance without a DB.

Server-side aggregation

Pro: one source of truth for median/avg math.
Con: every date change hits the API (fine at this size).

Client-side make/search filters

Pro: snappy typing/chips with no round-trip.
Con: filtered median is approximate (weighted from model medians) unless we re-query raw prices.

Top 10 make chips only

Pro: keeps the filter row usable.
Con: smaller brands need search — intentional declutter tradeoff.

REST + JSON

Obvious to inspect in DevTools; good fit for a read-only internal explorer. No GraphQL/gRPC overhead for this case.

No auth

Treated as a localhost internal tool. Would add SSO/basic auth before any shared deploy.
